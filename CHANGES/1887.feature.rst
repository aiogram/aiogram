Added :mod:`aiogram.test` — an integration testing toolkit for bots, available as the
``aiogram[test]`` extra and registered as a pytest plugin.

Updates are fed through a real :class:`aiogram.dispatcher.dispatcher.Dispatcher`, so
filters, middlewares, dependency injection, FSM and Scenes run as they do in production,
while a stateful fake Telegram answers every Bot API call and applies it to an isolated
in-memory world.

Declare the world with :class:`aiogram.test.Blueprint` — chats, users, memberships
(including the bot's own status in a group), forum topics, business connections,
communities and invite links — then drive it through actors (``await user.send("/start")``,
``await user.reply(message, "text")``, ``await user.click(button)``,
``await user.follow_deep_link()``, ``await user.promote(**rights)``) and assert on the
resulting chat state or on the recorded calls. There is a trigger for every
:class:`aiogram.types.Update` variant, so no registered handler is unreachable from a test,
including ``stop_message_generation()`` for ``stopped_message_generation``, which always
arrives in the user's own private chat with the bot, the only chat ``sendMessageDraft``
targets.
Joining a group or adding the bot to one now also delivers the ``new_chat_members`` service
message a real client shows alongside the membership update, in the order Telegram posts
the two — pass ``service_message=False`` for the previous single-update behavior. A
misdirected ``click()`` — a button that genuinely exists, in some chat the actor forgot to
``.in_()`` — is named in the failure instead of reading identically to a plain typo in
``callback_data``. ``promote()``/``demote()`` take dispatcher data through a keyword-only
``data=`` mapping rather than competing with rights for ``**kwargs``, and a right
``promote()`` does not recognise — a misspelled ``can_pin_message`` — raises ``TypeError``
naming the ones that do exist instead of silently granting nothing.
A user's own private chat with the bot does not have to be declared at all: Telegram lets
anyone open one, so it opens on demand, shaped exactly like a declared one — on the paths a
user drives, which are the only ones where it can happen, since a bot cannot write into a
private chat first. It can also be opened directly with
:meth:`aiogram.test.World.ensure_private_chat`, which accepts the user's spec, its resolved
state, or a bare id, and :meth:`aiogram.test.BotTestEnvironment.chat` now opens the same
chat for a bare id naming a declared user, agreeing with the actor path instead of raising
where that path already succeeds. Deep links are followed the way tapping them behaves —
including a bare profile link, which replays as a plain ``/start``, and a link carrying an
explicit ``start`` with a non-empty value alongside anything else, which a real client reads
as that start.
Every other link format `Telegram documents <https://core.telegram.org/api/links>`_ is
classified against that spec and refused by name with what a real client does instead — an
invoice link and a boost link point at ``pay()`` and ``boost()``, a phone-number link is told
apart from a chat invite link, a prefilled-draft link names the text it left unsent, and a
channel's web-preview link is told apart from a direct Mini App link despite sharing its
``t.me/<name>`` shape — rather than being quietly downgraded or lumped into one generic
rejection, and a ``start`` payload outside the characters Bot API deep linking allows is
refused rather than delivered to the handler, unless the call opts out with
``validate_payload=False`` to replay a payload exactly as a real client delivered it.

Results are mounted to the bot exactly as parsed responses are, so shortcuts work on them
and on every object nested inside them, while the objects a test hands to a call stay the
test's own — the world keeps copies of them, and hands out copies of what it stores.
A chat's ownership is now enforced per chat rather than only at whole-registry assignment:
registering a :class:`aiogram.test.ChatState` that already belongs to another world raises,
whether it arrives through ``world.chats = other.chats``, through
``world.chats = dict(other.chats)``, or one item at a time — a live registry holds the
donor's own chat objects, and installing any of them here would rewrite ``chat.world`` on
what the donor world still holds, silently binding its messages to this world's bot instead.
Moving a chat between worlds is still possible, said explicitly, and the refusal spells out
every way that actually works: a deep copy, a fresh chat built from the blueprint
declaration, or this very object given up by the donor — each detached with
``chat.world = None`` before it is registered, which is the step the message used to leave
out, so following its advice landed on the same refusal again.

The world models the surfaces a bot's own logic depends on: sending, editing, moving,
pinning and deleting messages; polls and reactions; chat administration and membership,
including join requests and administrator rights — which are declared and granted as a whole
and reported per chat type rather than assumed — and member permissions, which carry the Bot
API's own couplings, so granting the right to send stickers grants the right to send messages
unless ``use_independent_chat_permissions`` says otherwise; the bot's own profile; forum
topics; business connections; invite links; sticker sets; and Telegram Stars and gifts, where a payment
credits a real balance and a refund resolves the charge id the handler was given. Methods
it does not model are recorded and answered with a schema-valid result derived from their
declared return type, so no test has to pre-register results just to keep the bot running, and
:meth:`aiogram.test.BotTestEnvironment.on` overrides any of them per test. An override can
now be targeted to a call's resolved fields (``chat_id=alice.id``) or an arbitrary predicate
(``.where(...)``), so two calls of the same method made from one trigger — a group message
and a per-player DM — can be given different outcomes without reordering the production
code to serve the interesting recipient first; a rule whose fields do not match a call is
skipped without spending its ``times`` budget. ``env.blocked(chat_id=...)`` is the common
case of one recipient refusing every method a block stops, not only delivery: the
``editMessage*`` family, ``pinChatMessage`` and the whole reaction family
(``setMessageReaction``, ``deleteMessageReaction``, ``deleteAllMessageReactions``) are covered
too, since a bot that reacts to a failed send by editing its previous message or clearing the
reaction it left there must be seen to fail at that as well — see
:data:`aiogram.test.BLOCKED_METHODS`, whose one documented exclusion is
``deleteMessage`` (a bot dropping its own leftovers is not *delivering* anything, so a block
does not guess at it). A **delivery** method addressed by ``user_id`` rather than ``chat_id`` —
``sendGift`` — is blocked too, while on the other methods ``user_id`` names a participant
rather than the addressee and is not keyed, so clearing the blocked user's reaction in a group
the bot can still reach goes through. A block or an override addressed by chat id still catches
a call the bot spells as ``@username``, and vice versa. It is scoped with ``with`` or
cancelled by hand through the handle every ``.on(...)`` call now also returns, and raises the
shared :data:`aiogram.test.BLOCKED_BY_USER` message by default. Every recorded call,
including one an override goes on to refuse, is logged **before** the override answers it, so
a test can assert both that the bot tried to reach the right addressee and that it coped with
being refused. ``env.assert_overrides_consumed()`` names any declared override that never
answered a call — the usual reason a bot behaves as if it were never declared — and the same
listing is appended to a ``wait_for``/``wait_for_message_in`` timeout. Only rules a test wrote
by hand are listed: ``blocked()`` is one *simulation* spelled as a rule per method a block
stops, of which the bot is meant to take one or two, so those are excluded entirely — otherwise
the assertion could never pass inside the very block it is documented for, and every timeout
there ended in forty lines about methods nobody expected to be called. The
documentation names which surfaces are deliberately left that way, and which are merely
waiting for demand.

Failures are two things, not one. A call the real Bot API would refuse fails as the
:class:`aiogram.exceptions.TelegramBadRequest` it fails as in production, carrying
Telegram's own wording, so a bot's ``except`` branch is testable. A gap in the *test's* own
setup — a user, chat, sticker set, poll or business connection the blueprint never declared
— raises :class:`aiogram.test.WorldLookupError` instead, and nothing converts it: it
propagates and fails the test with a message that says what to declare, rather than being
handed to the bot's error handling to swallow. That includes a chat the bot itself calls
into: writing to an undeclared chat fails the test and names the chats that do exist,
instead of arriving as the "chat not found" a bot's own "the user blocked me" branch would
catch and pass. A test that wants that branch declares the refusal outright with
``env.on(SendMessage).raises(...)``. Feeding an update whose carried message collides by id
with a different message the destination environment already holds fails the same way,
naming both messages, rather than silently keeping the one already there and leaving a
handler working on a message the world will never store.

Where an update actually went is now inspectable, not only what came back: the new
:attr:`aiogram.test.BotTestEnvironment.last_route` reports whether the dispatcher considered
the most recently fed update handled, which handler and router won, and the exception raised
inside the middleware chain or the handler even when the bot's own error handler goes on to
swallow it — so an update lost in a middleware, or caught by a catch-all logging handler
instead of the one under test, no longer looks identical to one that reached its intended
handler. The diagnosis is scoped to one **trigger** rather than one update, since one thing a
test does — ``member.join()``, most of all — is routinely more than one: a bare call opens
its own scope and an explicit :meth:`~aiogram.test.BotTestEnvironment.trigger` block groups
several; :attr:`~aiogram.test.BotTestEnvironment.routes` lists every record of that scope and
``last_route`` is the newest record **carrying an exception**, else the newest **handled** one,
else the newest of any kind — so a handler that raised and had its exception swallowed by the
bot's own error handler is reported rather than hidden behind a later update of the same
trigger that went fine. A scope belongs to the **task** that opened it rather than to the
environment, so two triggers running at once under ``asyncio.gather`` neither share nor erase
each other's records, an unrelated feed is not absorbed into a block another task holds open,
and an update fed to a second environment from the first one's handler starts a scope of its
own; outside any block, ``routes`` reports the trigger that completed last, and a concurrent
test asserts per branch by giving each branch a ``trigger()`` block of its own.
:meth:`~aiogram.test.BotTestEnvironment.assert_handled_by` is the assertion spelled directly,
matched against the winning handler's qualified name, and scans every record of the scope —
so it no longer fails a bot that correctly handled a ``chat_member`` transition just because a
``new_chat_members`` service message delivered alongside it went unclaimed — failing with all
of them dumped, including any exception raised and swallowed along the way.

File content is supported where it can be honest: a file uploaded as a
:class:`aiogram.types.input_file.BufferedInputFile` can be downloaded again in the same
test, and other content is declared with :meth:`aiogram.test.Blueprint.add_file`.
Downloading content the environment does not hold raises rather than returning empty
bytes, which would be indistinguishable from a genuinely empty file.

Bots that keep their own background tasks change the world after a trigger returns, so the
toolkit ships the waiting helpers such a test would otherwise hand-roll:
:meth:`aiogram.test.BotTestEnvironment.wait_for` polls any condition and returns whatever
truthy value it produced, and ``chat.wait_for_message(...)`` waits for a matching message
in one chat — or in one forum topic, returning the newest match. Both take an optional
``description`` as their second positional argument, since for the lambdas they are written
with it is the only thing a failure can say about what was expected, and both give up with a
:class:`aiogram.test.WaitTimeoutError` — a :class:`TimeoutError` — whose message says what
was awaited and what the chat holds instead. How long they wait is one setting per
environment, ``BotTestEnvironment(..., default_wait_timeout=...)``, with an explicit
``timeout=`` still winning per call. The pytest plugin reads it from its own overridable
``bot_env_wait_timeout`` fixture, so a suite changes it without reconstructing ``bot_env``.
``wait_for`` also takes ``watch=`` — one chat, topic or user, or several — to dump their contents
into the timeout message, since the answer to "why did the condition never become true" is
usually in what the bot said instead. The new
:meth:`~aiogram.test.BotTestEnvironment.wait_for_message_in` is the broadcast form: it polls
several chats at once for a bot that fans one event out to many of them, returning a
``chat_id -> Message`` mapping once every one of them holds a match, and naming in its
failure only the chats that are still missing one. Both spell one vocabulary for what may be
watched — a chat or topic declaration, a live state, a **user** (standing for their private
chat with the bot, opened on demand), or a bare id — so the broadcast this exists for is
written with the list of ``add_user`` declarations a test already holds.

A test that leaves the bot's own background tasks running — a scheduler, a timer — can clean
them up explicitly with ``await env.drain(timeout=...)``, which cancels and awaits every task
the test itself spawned instead of letting asyncio complain about a destroyed pending task
after the test that caused it has already passed. A task already running is spared, and that
protection is now taken twice: once at construction, and again at this environment's first
asynchronous action, which is what keeps a session-scoped fixture's own background worker
alive across the first test in a session that calls ``drain()`` even though the (synchronous)
``bot_env`` fixture could not see it running yet. An environment with no snapshot at all —
built by the synchronous fixture and drained before it ever fed an update or handled a call —
owns nothing and cancels nothing, rather than treating every task in the loop as its own. A
drained task that failed on its own is no
longer swallowed: it now surfaces as :class:`aiogram.test.DrainedTaskError`, with the original
traceback chained, rather than only as asyncio's own "exception was never retrieved" noise —
including a task that died *before* the drain, which ``asyncio.all_tasks()`` does not list at
all, so the environment remembers every task created while it is live and inspects the finished
ones too. It is opt-in rather than automatic, since
the pytest fixture's teardown is synchronous and cannot await a cancellation, and cancelling
tasks a test never mentioned as an invisible side effect of a fixture going out of scope
would turn a stopped scheduler into a mystery.

A rich message sent as blocks is stored with those blocks in the shape Telegram returns, nested
blocks and media included, instead of as an empty rich message; ``editMessageText`` replaces
text with rich content and back, and ``click()`` and ``follow_deep_link()`` reach buttons
anywhere inside rich content as well as on the inline keyboard. Rich content given only as
``html`` or ``markdown`` is stored without blocks, since that rendering is Telegram's own.

A restricted user is reported with a truthful ``is_member``: restricting someone who never
joined leaves them absent and uncounted, and a restricted member who leaves or rejoins keeps
the restriction. Restricting with every permission granted lifts it, a restriction or ban with
no end reports ``until_date`` as the Unix epoch instead of a fixed date, a basic-group ban has
no end, an end date no longer outlives the status it belonged to, and ``unbanChatMember``
honours ``only_if_banned``.

An ephemeral message is modeled as Telegram shows it: a send with
``ephemeral_message_parameters`` returns ``message_id`` 0, an ``ephemeral_message_id`` and the
``receiver_user``, stays out of ``chat.messages`` and is read back with
``chat.ephemeral_messages(user)``. Only its receiver can press its buttons, the
``editEphemeralMessage*`` and ``deleteEphemeralMessage`` methods act on it instead of being
record-only, and ``send(..., ephemeral=True)`` delivers an ephemeral command whose
``message.reply()`` answer is ephemeral too, with replies to ephemeral messages validated as
the Bot API describes.

The world has a clock a test controls with ``await env.advance_time(...)``. It starts at the
real time, so dates a bot computes from ``datetime.now()`` work, or at a fixed
``clock_start=`` (the ``bot_env_clock_start`` fixture) for reproducible dates, and stands still
otherwise: dates no longer advance a second per update. The time limits the Bot API documents
are measured against it — mutes and bans expire (with Telegram's "less than 30 seconds or more
than 366 days is forever" rule, and a ``timedelta`` ``until_date`` counted from the clock),
polls with ``open_period`` or ``close_date`` close on schedule and send a ``poll`` update, live
locations stop being editable, messages older than 48 hours cannot be deleted, a private-chat
dice cannot be deleted for 24 hours, old business messages cannot be edited, a pre-checkout
query must be answered within 10 seconds and an ephemeral command within 15.

Modeled methods follow the rules the Bot API states for them. ``sendMediaGroup`` stores each
item's media and caption under one ``media_group_id`` and takes 2-10 items; a reply to a
message that does not exist fails unless ``allow_sending_without_reply`` allows it, through
``reply_parameters`` or the deprecated top-level fields, and a reply in another chat is carried
as ``external_reply``; a single copy or forward leaves its album, while ``forwardMessages`` and
``copyMessages`` keep each album together, and a copied poll is a poll of its own; a venue
stores the location it was sent with and an invoice the total of its prices; copies and
forwards land in the requested topic as new messages that keep no reply, edit or protection
from the original, a forward of a forward keeps its first origin and a forwarded channel post
names its signature in the origin, copies carry the new caption, its entities, the inline
keyboard and their own reply, and service, protected, invoice, paid media and giveaway messages
are refused where the Bot API refuses them; ``unpinChatMessage`` without an id unpins only the
newest pin; editing text or a caption fails on a message without that content, and every edit
sets ``edit_date``, the bot edits only its own messages outside channels and, in business
chats, the account's but not the customer's; ``editMessageMedia`` keeps an album item to its
album's kind, and ``sendMediaGroup`` keeps documents and audio apart from other media; a quiz
is copied only with a known answer; dates the bot passes count in whole seconds; sends and
media edits store the spoiler and caption placement flags; quizzes keep all their
``correct_option_ids``, regular polls allow revoting by default and ``stopPoll`` stores its
keyboard; hiding the General topic closes it and reopening unhides it; an empty topic name
keeps the name; business messages are numbered per account, so ``deleteBusinessMessages`` finds
their one chat; and checklists keep their title and tasks. Creation service messages cannot be
deleted. Synthesized files get distinct ids and keep a file id the request passed with its
unique id, dice carry their emoji and a value in its range, enumerated strings take valid
values, booleans are false, rich voice note blocks convert, star transactions report the charge
id, a positive amount and the user, and an administrator the bot promoted reports
``can_be_edited``, while one known to be promoted by someone else cannot be edited, demoted or
titled by the bot, and a star payment is refunded only to the user who paid it. A declared
world matches one built through the API: declared permissions get the documented defaults,
declared topics are created by the bot, and ``Blueprint.add_poll`` declares a poll.

Actor triggers produce only updates Telegram would deliver. ``click(..., message=m)`` presses
the button on the stored version of ``m`` in the actor's chat and refuses a button it does
not carry; a user's ``edit`` sets ``edit_date``, changes only the fields passed and refuses a
message the user did not send, and an edited message fed by hand replaces the stored one;
``vote`` refuses option ids the poll does not have, several options on a single-answer poll
and a changed or retracted vote where revoting is not allowed; ``inline_query`` sets
``chat_type`` and accepts ``fields=``; ``guest_message`` carries a ``guest_query_id`` the bot
can answer; ``update_subscription(state=...)`` takes one of the documented states; a
subscription ``pay()`` sets ``subscription_expiration_date`` and ``is_first_recurring``; and a
``business_connection`` update names the account owner. Routing diagnostics no longer report a
handler that raised ``SkipHandler`` as the one that ran, and ``drain()``
no longer reports an exception the bot already retrieved.

.. warning::

    This is a **proof of concept**. The module name, the fixtures, the blueprint and actor
    APIs, the world model and the set of modeled methods are all subject to change, and may
    change incompatibly between releases while the design settles.
