# 02 — Butcher (Rust): two input adapters, one IR

Decisions: **D6a** two input adapters (HTML docs + OpenAPI schema) feeding one IR; **D6b** the generator is
written in Rust (`cargo xtask butcher`); **D6c** compat ledger reset at 4.0, rolling window afterwards.
The Python butcher (3.x) is retired; its Rust successor keeps the name **butcher**.

## 1. Legacy butcher today (3.x, Python; what we replace)

Source: the sibling repo `aiogram/butcher` (v0.1.23, ≈4.3k LOC + 2.1k tests; requests, lxml, PyYAML, Jinja2,
libcst, black). Not installed in this checkout (`aiogram-cli` only ships the `develop` plugin).

| Stage | What it does |
|---|---|
| `parse` | `requests.get` docs page → lxml. Walks `a.anchor` under `h3`/`h4`; an `h4` with a one-word title is an entity, lowercase first letter means a method. Tables zipped by header; method `required` from the Yes/Optional column, type `required` from an `Optional` prefix plus a fixed 10-char slice. Descriptions stored as plain/HTML/RST. Version from the first `recent-changes` `h4`. Writes `.butcher/schema/schema.json` |
| `parse-patch URL` | merges a preview page (e.g. corefork) as an "Upcoming update" group |
| `refresh` | schema → `.butcher/{types,methods}/<Name>/entity.json`, **merged with the previous state** (§4) |
| `apply all` | registry init (enums, 3 resolver tiers, unions) → libcst transformers rewrite `aiogram/types|methods|enums`, `__init__` exports, `client/bot.py`; 6 Jinja templates for docs RST only; black at 99 cols |

**Heuristics that drift** (all over prose):
- type strings (`Array of X`, `X or Y`, capitalised word means entity ref)
- return types: 14 ordered regexes, first match wins, 3 manual `returning` overrides
- consts: 3 regexes
- subtype lists: `- (.+)` over the parent description
- enums: `parse`/`multi_parse` regex `findall` over field descriptions

A missed discriminator is only a warning, and enums can silently pick up the wrong members.

**Other pain**:
- F821 missing imports after apply (a whole skill exists for it).
- `Default` sentinels dropped in shortcuts (#1873).
- Generated files are also hand-edited inputs (CST merge keeps everything after the first `def`; custom attributes between fields and methods are dropped).
- No YAML schema validation: `tagged: true` in `MaybeInaccessibleMessage/subtypes.yml` is dead config.
- State is never cleaned up.
- Hand-written sites legacy butcher never touches: `Update.event_type`, `resolve_event_context`, `ContentType`, `Message.content_type`, old-param translation in `Bot` (`client/bot.py:337-353`).

**Overlays**:

| Overlay | Count | Contents |
|---|---|---|
| `aliases.yml` | 13 files, 189 shortcuts | Python `fill` expressions, `ignore`, `code` guards |
| `default.yml` | 69 | `Default(...)` |
| `replace.yml` | 88 | 70 annotation, 18 bases, 3 returning |
| `subtypes.yml` | 29 | 27 discriminators |
| `unions.yml` | 1 | |
| `extend.yml` | 1 | |
| `enums/*.yml` | 38 | 20 `multi_parse`, 11 `parse`, 7 `static`, 2 `extract` |

## 2. Inputs (two adapters)

| Adapter | Source | Strength | Weakness |
|---|---|---|---|
| **html** | `core.telegram.org/bots/api` (+ optional preview URL, e.g. `corefork.`, like `parse-patch`) | always current (10.4 today) | prose heuristics for returns/consts/subtypes/enums; no int widths, no multipart encodings |
| **openapi** | `<host>/bots/api.json` + `errors.json` (OpenAPI 3.2; corefork, 10.3 today) | structured: 23 discriminator mappings, 541 consts, 113 enums, int32/int64/double, constraints, 34 multipart bodies with `encoding`, return types via `mediaTypes`, error responses, errors catalogue | lags the HTML on staging; `core.` URL not live yet |

Both adapters produce the same **source IR** (`Type`, `Field`, `Method`, `Param`, `TypeRef = Prim|Ref|Array|Union`,
`Returns`, `Discriminator`, `Enum`, `Constraint`, `Doc`). Every inferred fact carries a provenance:
`{explicit | heuristic(rule_id) | overlay}`.

Upstream note: staging docs say *"This documentation and the schema are generated by a generator"* in
`tdlib/telegram-bot-api/tree/master/generator` (404 today). If that source is published, a third adapter for it
is the long-term input, and both of ours become cross-checks.

### Selection & cross-check per release

```
html  = adapter_html(core [+ preview])           # always run
oapi  = adapter_openapi(host)                    # run if reachable
if oapi.version == html.version:
    ir = merge(primary=oapi, structure_check=html)     # schema facts win; html must agree on entity/field/required sets
    report heuristic disagreements → fail on structural, warn on doc-only
else:
    ir = html                                          # schema lags
    fill heuristic gaps from the *previous* schema snapshot where the entity is unchanged
    mark release "html-only" in the IR header; overlay must resolve every heuristic the cross-check flagged before
```

So the regex heuristics (ported from legacy butcher) only decide anything for entities added since the last schema
version. Each release where both exist re-validates them: a heuristic that disagrees with the schema is a test
failure, not a silent drift.

## 3. Overlay (`butcher/overlay/*.toml`)

Strict schema: unknown keys are errors, and every reference is checked against the IR. Replaces all 7 legacy butcher YAML kinds:

1. Python names and aliases (`from` → `from_user`), keyword-safe names, and collision renames for reserved exact
   names (`bot` → `bot_user` on `ManagedBotCreated` / `ManagedBotUpdated`, D109); `check` fails on a new collision
   until a rename is configured.
2. Named enums for inline `enum`/`const` sets plus aiogram-only enums (`UpdateType`). The
   `extract`-style rule (enum from field names) is kept.
3. Datetime fields: an explicit list. The generator warns on an unlisted int field whose description matches `Unix time`.
4. Bot-level `Default(...)` per parameter.
5. Shortcuts: target method + **fill-DSL** (declarative, replaces inline Python), plus `ignore` and guards.
   Example: `chat_id = "self.chat.id"`, `message_thread_id = { expr = "self.message_thread_id", when = "self.is_topic_message" }`.
   Unexpressible shortcuts are marked `handwritten = true` and live in Rust `<type>_ext.rs` (D11).
6. Decode strategy for undiscriminated unions (12 today, 3 ever decoded): tag or predicate, otherwise `Unknown`;
   no declaration-order fallback (D107).
7. `Input*` twins (D18): of the schema's 74 `Input*`/output pairs, 67 are documented Bot API types (`InputSticker`,
   `InputPollOption`, `InputRichText*`, …) and are generated as they are. The other 7 exist only in the schema
   (`InputAcceptedGiftTypes`, `InputBotCommand`, `InputChatAdministratorRights`, `InputChatPermissions`,
   `InputLinkPreviewOptions`, `InputMessageEntity`, `InputSwitchInlineQueryChosenChat`). They are the request-side
   shape of the documented type and get **merged** into it:
   - one class with the union of fields;
   - a field is required only where both shapes require it (`ChatPermissions` stays all-optional, as in 3.x);
   - response-only `const: true` is dropped;
   - request-only fields go through the ledger (`can_send_media_messages`).
   The merge list is computed (schema `Input` + X where X is documented and `Input` + X is not) and `check`
   reports changes to it. The IR keeps **direction-specific** requiredness and constants even for merged twins
   (D118), for diagnostics, the fake and the encoder.
8. Hot fields for the sparse layout (01 §3.1).
9. Heuristic overrides for html-only releases (returns, consts, subtypes, enum members).
10. Docs extras.

One-off migration: `cargo xtask butcher import-legacy` converts `.butcher/**` YAML into the overlay and
`entity.json` markers into the ledger (§4). The Python `fill` expressions are translated to the DSL, and any it
can't parse are flagged for manual work. Then `.butcher/` is deleted.

## 4. Compat ledger (`butcher/ledger.toml`)

Legacy butcher's backward-compat memory is `entity.json` used as a state store:
- fields that vanish upstream are re-appended with `deprecated = {version, date}`;
- removed entities get `meta.deprecated` and are never deleted;
- positional params that became optional get `keep_position` (currently `chat_id` on 15 send* methods, so
  `bot.send_message(chat_id, text)` keeps working).

Neither input contains this state, so v4 keeps it as an explicit, committed ledger, separate from the IR:

```toml
[[removed_field]]            # written by `butcher diff` when a field disappears upstream
entity = "SendMessage"; field = "disable_web_page_preview"
removed_in = "7.0"; removed_on = 2023-12-29; drop_after = "…"   # computed from the policy below
replacement = "link_preview_options"   # optional; drives the runtime translation table

[[removed_entity]]
entity = "StoryAreaPosition"; removed_in = "10.4"; removed_on = 2026-11-09
```

**Policy (D6c)**:
- **4.0 reset**: every deprecated field and entity accumulated in 3.x is dropped and listed in the migration
  guide. That covers the 38 marked entities: 7.0 `reply_to_message_id`/`allow_sending_without_reply`/`disable_web_page_preview`,
  7.3 `Chat.*` fields moved to `ChatFullInfo`, `UserShared`, `KeyboardButtonRequestUser`, and more.
- **`keep_position` is dropped** (D100): every generated signature is keyword-only, so parameter order never matters
  and an optional field no longer has to move. The ledger keeps only `removed_field` / `removed_entity`.
- **Rolling window after 4.0 (decided)**: a removed field or entity stays, as deprecated, until **both** 12 months
  have passed since removal **and** 2 Bot API major versions have shipped after it (the later of the two). It is
  then dropped in an aiogram **minor** release, with a `removal` changelog fragment generated automatically.
  `butcher diff` computes `drop_after` per entry, and `check` lists entries that are due.
- The 4.0 reset is an explicit exception to D71's rolling rule (R28, 16).
- Deprecated items emit a **runtime `AiogramApiDeprecationWarning`** (D72's subclass, R28) when set or read (generated in Rust) and a
  `.. deprecated::` note in the stub docstring (D79). `replacement` entries generate the old→new parameter translation that is
  hand-written in `Bot` today.

## 5. Generator (`crates/butcher`, run via `cargo xtask butcher`)

```
crates/butcher/src/
  sources/{html.rs, openapi.rs, errors.rs}   # scraper / serde_json
  ir.rs  overlay.rs  ledger.rs  merge.rs  diff.rs
  emit/{rust.rs, pyi.rs, python.rs, enums.rs, error_reason.rs, rst.rs, tests.rs}
  templates/*.jinja                           # minijinja (Jinja-compatible; docs templates port as-is)
```

| Command | Does |
|---|---|
| `fetch` | downloads sources into a cache (not committed); raw source bundles are attached to releases as immutable assets (D118) |
| `build` | sources → per-adapter IR (`ir.html.json`, `ir.openapi.json`) + merged IR + overlay + ledger → `butcher/snapshots/<ver>/` (**committed**, one per API version; this is the version archive Telegram doesn't keep), with a **manifest**: URLs, fetch time, sha256, tool and overlay versions, html-only flag (D118) |
| `emit` | writes generated files whole; hand-written code lives in separate `*_ext.rs` / `*_ext.pyi` / mixin-consuming modules that the generator never touches (§5.1) |
| `diff <old> <new>` | structured change list → ledger updates, `CHANGES/*.misc.rst`, PR body |
| `check` | CI gate, **offline** (D118): regenerate from the committed IR and fail on diff; overlay/ledger validation; heuristic-vs-schema disagreements. A scheduled online job re-extracts the sources and diffs them against the committed per-adapter IR |
| `import-legacy` | one-off migration (§3, §4) |

Emitted:
- **Rust**: `crates/aiogram-core/src/generated/**` (types, methods, unions, enums, encoders, shortcuts, deprecation warnings).
- **Python**: per-type/method re-export modules + `.pyi` stubs and the `__init__` exports (§5.2), `aiogram/enums/*.py`, `aiogram/enums/error_reason.py` (`ErrorReason` + template table) from `errors.json` (D47),
  `Bot` async method wrappers, and the sites that are hand-written today (`Update.event_type`,
  event-context resolution, old-param translation).
- **Docs**: thin `docs/api/**.rst` index pages; the reference itself is sphinx-autoapi over the `.pyi` stubs (D79, R29).
- **Tests**: per-type JSON round-trip, per-method encode, per-shortcut fill, deprecation warnings.
- **Forward-compat**: an `Unknown<Union>` variant per union (carrying the variants' common fields), tolerant enums,
  and the unknown-update-type path ([10](10-forward-compatibility.md)).

### 5.1 Hand-written code next to generated code

Today you add methods by hand to generated files and legacy butcher keeps them while updating the generated parts: 26
hand-written methods in 12 type classes, plus hand code in `client/bot.py`. v4 keeps that ability, but on the Rust
side (decision **D11**). There is no Python facade per type.

| Hand-written today | v4 home |
|---|---|
| `User.full_name/url/mention_html/mention_markdown`, `Chat.full_name/shifted_id`, `Contact.full_name`, `Message.get_url`, `as_reply_parameters`, `as_ephemeral_message_parameters`, `Downloadable.file_id` | hand-written Rust: `crates/aiogram-core/src/types/<type>_ext.rs` |
| `Message.html_text/md_text/_unparse_entities`, `MessageEntity.extract_from` | Rust entities module (06), exposed from `message_ext.rs` |
| `Update.event_type/event/__hash__` | **generated** from the IR (update fields) |
| `Message.content_type` + `ContentType` | **removed** (2.x leftover, [11](11-removals.md)); `send_copy` uses an internal content-kind table |
| `Message.send_copy` | **generated** from an overlay mapping `content_type → method + field map`; a new content type with no mapping fails `check` |
| `InputFile` family (`read()` = async file/HTTP streaming) | stays **plain Python** (`aiogram/types/input_file.py`); not a pyclass; the encoder recognises it with `isinstance` |

**Mechanics**
- Generated Rust (`src/generated/**`) is always fully regenerated: no regions and no merging. Hand code lives in
  separate `#[pymethods] impl Message { … }` blocks in `*_ext.rs`, using PyO3's `multiple-pymethods` feature.
  If a hand-written name collides with a generated one, compilation fails.
- **Stubs**: each `<type>_ext.rs` has a sibling `<type>_ext.pyi` fragment declaring its Python signatures. The
  generator merges these fragments into the generated `aiogram/types/<type>.pyi`, and `stubtest` in CI catches
  drift between the Rust code and the fragments. PyO3's own stub generation is still experimental, so we don't
  rely on it.
- **Parity tests**: every ported helper gets tests derived from today's Python behaviour, e.g. `mention_html`
  escaping matching `html.escape`.
- `Bot` (`client/bot.py`) stays Python. The generated async method wrappers go in a separate generated module
  that is fully regenerated (e.g. a `_BotMethods` mixin). The hand-written `Bot` class (`__init__`, context manager,
  `download`, old-param translation hooks) inherits from it, so `bot.py` needs no markers either.
- Python is still extensible for **users**: they can subclass a type in Python and register it for decoding (01 §3.5).

**Trade-off accepted**: adding or changing a helper on a Telegram type needs Rust. In return: one class per type
that the decoder creates directly (this removes the subclass-instantiation risk from the spike), no Python class
per type, no marker or merge machinery, and native-speed helpers. Per-type Python *modules* stay as thin
re-exports (§5.2), and nothing imports them on the default path.

### 5.2 Python module layout (D16)

**Decided: keep the 3.x layout.** There is one module per type and per method, not one merged module.

| File | Content |
|---|---|
| `aiogram/types/<type>.py`, `aiogram/methods/<method>.py` | one-line re-export from `aiogram._core`; loaded only when deep-imported |
| `aiogram/types/<type>.pyi`, `aiogram/methods/<method>.pyi` | generated stub with the `<type>_ext.pyi` fragment merged in |
| `aiogram/types/__init__.py`, `aiogram/methods/__init__.py` | import **directly from `aiogram._core`**, never through the submodules, so startup reads no per-type files |
| `aiogram/types/__init__.pyi` | `from .message import Message as Message` re-exports |

- Every pyclass sets `module = "aiogram.types"` / `"aiogram.methods"`, so pickle, repr and docs paths don't depend on
  the file layout.
- Generated docs show `from aiogram.types import X` / `from aiogram.methods import X` as **the** import. The deep path
  becomes a footnote, which reverses today's order (`docs/api/methods/*.rst:30-31`). New code then stops depending on
  deep paths, so a merge stays cheap if it is ever wanted (5.0 at the earliest).

Single merged module, rejected:
- It breaks every deep import (the docs teach them first today) and gives users nothing, since the short path
  already works.
- Its benefits are free here anyway. Import cost is avoided by the direct `_core` import, the pickle path by
  `module=`, and cross-imports are computed from the IR.
- The one stub would be ≈1.3–1.5 MB *est.* and growing ≈330 KB a year (`types` sources: 835 KB at v3.0, 1.38 MB at
  v3.20, 1.9 MB now). In ≈3 years it would cross PyCharm's 2.5 MB code-insight limit (`idea.max.intellisense.filesize`),
  which would force a private per-type stub split anyway.
- Bot API bump diffs would land in one huge file that GitHub may not render.
- It loses the 1:1 `message.rs` / `message_ext.rs` ↔ `message.pyi` ↔ `message.rst` mapping.

**Emitter rules (13 B20, B21):** generated Rust binds each field value to a local (or pushes it) before building a
struct or vec; `Self { a: x(a)?, b: x(b)?, … }` emits cleanup code that grows with the square of the field count
(`Message::field_values` 45 980 → 2 355 IR lines). Class-independent logic lives in shared non-generic helpers.
Per-class shared behaviour is emitted as trait impls whose `Self` is the class (08 §7 item 13).

Formatting: `prettyplease`/`rustfmt` for Rust, `ruff format` for Python, so generated output is stable and
`check` is deterministic. Imports are computed from the IR (each emitted file knows its references), which
removes the F821 class of bugs.

## 6. Risks

- **Two adapters to maintain.** Mitigated because the html adapter only *decides* for entities newer than the last
  schema; otherwise it is a structural cross-check.
- **Schema source churn or upstream generator published**: adapters isolate the IR; add the upstream adapter
  when it appears.
- **Helper contributions need Rust**: accepted (D11); most contributions (dispatcher, FSM, filters) stay Python.
- **Fill-DSL coverage**: the `import-legacy` report shows the gap. Unexpressible shortcuts become hand-written Rust (D11).
- **Schema source lag** (was O7): on 2026-11-16 `corefork.telegram.org/bots/api.json` was at 10.3 while the live
  API was 10.4, and `core.telegram.org/bots/api.json` served the HTML fallback. The dual adapters cover this (§2).
  Watch for the upstream generator (`tdlib/telegram-bot-api/tree/master/generator`, cited on corefork, 404 today).
- **No explicit license on the schema**: the repo commits only derived IR snapshots, as `entity.json` is today; raw
  source bundles live as release assets (D118).
