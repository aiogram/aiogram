# 10 — Forward compatibility: new API data must never break a bot

## 1. Problem (reproduced on dev-3.x)

Telegram adds union members, enum values, fields and update types between aiogram releases. Today:

| New upstream thing | 3.x behaviour |
|---|---|
| unknown **union tag** (e.g. `ChatMember.status = "superadmin"`, new `MessageOrigin`/`BackgroundType`/`PaidMedia`/`RichBlock` kind) | `ValidationError` → `ClientDecodeError` for the **whole `getUpdates` batch** (up to 100 updates) |
| … in polling | `_listen_updates` (`dispatcher.py:222-236`) treats it as a network error: backoff, retry the same offset → **the bot is stuck forever** until aiogram is upgraded |
| … in a method response (`getChatMember`, `getChat`…) | the call raises although Telegram succeeded |
| unknown **enum value** in a `Literal`/enum-typed field | same `ValidationError` |
| unknown **field** | kept in `model_extra` (`extra="allow"`), OK |
| unknown **update type** (new top-level key) | parses, but `Update.event_type` raises `UpdateTypeLookupError` (`types/update.py:251`) |

Reproduction: `bot.session.check_response(method=GetUpdates(), content='{"ok":true,"result":[<valid message>, <chat_member with status "superadmin">]}')`
raises `ClientDecodeError: … Input tag 'superadmin' found using 'status' does not match any of the expected tags`.

## 2. Goals

1. No upstream addition ever stops update delivery or fails a successful API call.
2. Each update is decoded on its own. One bad update never affects the others.
3. Raw data is always reachable: for the whole update and for any object, unknown or not.
4. Degradation is visible: logged once, observable by handlers, and optionally strict (tests, CI).

## 3. Design (v4, Rust decoder)

### Layer 1: tolerant schema (expected evolution never fails)

Generated by butcher for **every** union and enum:

- **Unknown union variant**: each discriminated union gets `Unknown<Union>` (e.g. `UnknownChatMember`,
  `UnknownMessageOrigin`). It carries the tag value, every field the variants have in common (from the IR, e.g.
  `ChatMember.user`), and the raw JSON. `isinstance` chains keep working; an unknown tag is no longer an error.
- **Undiscriminated unions** (`MaybeInaccessibleMessage`, `ReplyMarkup`-like): tag or overlay predicate, otherwise
  the `Unknown…` variant; no declaration-order fallback (D107, revises D85).
- **The nearest decoded union absorbs malformed data (D107)**: a malformed member of a *decoded* union becomes
  `Unknown…` carrying `.decode_error` and its raw value, and the rest of the update stays usable. Failures outside
  any union fall to Layer 2. `Unknown` variants exist only for unions that are decoded (MaybeInaccessibleMessage,
  ChatMember results, MenuButton results, every tagged union); request-only unions with primitive members (ChatId,
  DateTime, InputFile, …) get none.
- **Enums**: values outside the known set decode to plain `str` (Rust `Unknown(Box<str>)`). Fields are typed
  `ChatType | str` in stubs, which matches today's `use_enum_values` runtime.
- **Unknown fields**: kept as a raw slice, exposed via `obj.raw` (`model_extra` is a deprecated alias returning unknown fields only), readable as attributes with a one-time deprecation warning for one D71 window (D105), and round-tripped by `to_json()` / `to_dict()`.
- **Unknown update types**: `update.event_type` returns the actual key (e.g. `"brand_new_update"`) instead of
  raising; `update.event` returns `UnknownEvent(type, raw)`. Telegram only delivers types listed in
  `allowed_updates`, so a warning fires when `unknown_update` has handlers but `allowed_updates` is derived (R13).

### Layer 2: per-update isolation (unexpected breaks are contained)

For genuinely breaking changes, e.g. a required field missing or a field changing type:

- `getUpdates` decodes `result` **element by element** in Rust. A failing element becomes
  `Update(update_id=…, raw=…, decode_error=UpdateDecodeError(path, message))`. The id is extracted even when the rest is
  invalid. Polling **always advances the offset**. Delivery stays best-effort, not exactly-once (R13, 12 §5).
- The webhook decoder does the same.
- Dispatch: undecodable **and** unknown-type updates go to a new observer, `router.unknown_update`, with the raw event.
  `dp.update` outer middlewares still see them. If nothing handles them, they're logged and dropped. In addition, the
  `errors` observer receives each decode failure as an `ErrorEvent` with `phase=DECODE` and the `UpdateDecodeError`
  (D49), so existing error handlers notice. `dp.runtime_errors` (D50) is only for errors outside update handling.
- **Method responses**: the call returns the decoded value when Layer 1 suffices. When it doesn't, it raises the 3.x
  `ClientDecodeError`, which gains `.raw` with the raw `result`; there is no new `TelegramDecodeError` class (PD-29;
  D47: no new exception classes). Telegram did succeed, so callers can recover from raw.

### Layer 3: raw access everywhere

The Rust tree already keeps the raw buffer for laziness (01 §3.1), so raw access is free:

| API | Returns |
|---|---|
| `update.raw_json` | `bytes`: exact payload as received |
| `obj.raw` (any object, incl. nested) | a **fresh `dict` on every access**, decoded from its slice (D108); mutating it changes nothing |
| `obj.raw_json` | `bytes` slice of that object for wire objects; canonical `to_json()` bytes for constructed or `replace()`d objects (D108) |
| `UnknownX.raw` / `UnknownEvent.raw` / `UpdateDecodeError.raw` | same, for the degraded case |
| `ClientDecodeError.raw` | raw `result` of a method call (PD-29) |

Handlers can read new fields before aiogram supports them (`message.raw.get("new_field")`), and
`model_extra` stays as a deprecated alias returning the unknown fields only (`{}` when none) for one window (D91, R06).

### Visibility and strictness

- First occurrence per `(entity, field or tag)` logs one `WARNING` on `aiogram.event`: "unknown ChatMember status
  'superadmin' (API is newer than aiogram 4.x / Bot API 10.4), delivered as UnknownChatMember". After that, a counter
  is kept (exposed for metrics).
- `DecodePolicy` on `Bot`/`Dispatcher`: `"lenient"` (default) or `"strict"` (any Unknown or decode error raises).
  aiogram's own test suite runs strict, so butcher misses surface in CI.
- Butcher `check` replays a corpus of recorded updates under strict mode for each new API version. Corpus tests
  with a known schema always run strict (19 §8).

## 4. What this costs

- Typing: unions gain an `Unknown…` member. Exhaustive `match` statements that type-check against today's union
  will flag the new member. That's intended, and it's a 4.0 note in the migration guide.
- Runtime: nothing measurable. The unknown branch only runs on unknown data, and raw slices already exist.
- Shortcuts on unknown variants: only those that depend on the common fields (e.g. `UnknownChatMember.user`).

## 5. 3.x mitigation (pure Python, see 09)

- **Per-update isolation in polling** ([3x-01](../plans/3x-quick-wins/3x-01-polling-poison-isolation.md), 09 #21):
  the batch keeps its fast path; only when `bot(GetUpdates)` raises `ClientDecodeError` is `result` decoded as raw
  JSON and each `Update` validated separately (PD-28). A poison update is logged and the offset **advances** past it,
  which removes the "stuck forever" failure. The boundaries are the owner-signed record in
  [A-03](../plans/A-contracts/A-03-poison-update-decision.md); its "emit to `errors`" decision (Q6) feeds a synthetic
  `ErrorEvent(update=Update(update_id=<id>), exception=<ValidationError>)` through `dp.errors` with the usual
  kwargs, the 3.x precursor of `phase=DECODE` (D49). Webhook poison updates are 3x-02 (held back).
- **Unknown union tags** ([3x-18](../plans/3x-quick-wins/3x-18-unknown-union-fallback.md), 09 #23): a callable
  `Discriminator` with a fallback tag mapped to a generic `UnknownTelegramObject(extra="allow")` variant, emitted
  through the `.butcher` templates. Optional, larger change.
